# 자사 병원 28곳 인근 경쟁병원 확장 + 90분 순번 수집 설계

- 작성일: 2026-10-13
- 요청: 강남제이스타의원에만 있던 인근 경쟁병원을 나머지 자사 병원 28곳에도 붙인다. 대도시처럼 병원이 너무 많은 곳은 1차로 걸러 매일 수집 시간을 맞춘다.
- 사용자 확정 사항(2026-10-13)
  - 행정구역: 도 소속은 시, 특별·광역시는 구.
  - 병원당 경쟁병원은 최대 15곳.
  - 경쟁병원 몫 수집 시간은 하루 90분.
  - API 키 없이 웹 검색 방식으로 찾는다.
  - 사람 검수 없이 Claude가 확정해 바로 반영하고, 수정이 필요한 병원은 사용자가 따로 알려준다.

## 1. 경쟁병원 선정 (`find_competitors.py`, 온보딩 때 1회)

1. **검색**
   - 자사 병원마다 카카오맵 웹 검색을 "시도 시/구 진료과"로 한다. 구 이름이 겹치는 중구·서구·동구 때문에 시도를 붙인다.
   - 피부과·성형외과 병원은 두 진료과를 모두 검색한다.
   - 1~3페이지(최대 45곳)를 넘기며, 화면이 스스로 불러오는 검색 응답(`mapsearch/map`)을 읽는다. 별도 요청이나 우회는 하지 않는다.
   - 이 상위 노출 45곳이 대도시 1차 필터다.
2. **거르기**
   - 주소의 시도와 시/구가 같은 곳만 남긴다.
   - 카카오 분류(`cate_name_depth3`)가 같은 진료과인 곳만 남긴다.
   - 자사 병원 28곳은 카카오 ID와 이름으로 뺀다.
3. **15곳 고르기**
   - 15곳 이하면 전부 붙인다(원주 방식).
   - 넘으면 `(노출 순위 백분위 + 거리 백분위) / 2` 점수가 낮은 순으로 15곳을 고른다.
   - 동점은 카카오 장소 ID 순이다. 같은 입력이면 항상 같은 결과가 나온다.
4. **채널 대조**
   - 네이버는 `m.search.naver.com` 검색 결과의 `__APOLLO_STATE__`를 읽는다. 결과가 여럿이면 `PlaceListBusinessesItem`, 1곳이면 `PlaceDetailBase`로 나온다.
   - 구글은 지도에서 "이름 + 주소"로 검색하고, 못 찾으면 "이름 + 시도 시/구"로 다시 검색한다.
   - 채택 조건은 **주소 일치**(도로명+건물번호 또는 지번)와 **이름 일치**를 둘 다 만족하는 것이다. 같은 건물에 있는 다른 병원을 거르기 위해서다.
   - 구글에 영문 상호로만 등록된 곳은 주소 일치만 본다.
   - 못 찾은 채널은 빈 값으로 두고, 그 채널만 수집에서 빠진다(기존 규칙).
   - 캡차나 비정상 트래픽 화면이 나오면 즉시 중단한다. 다시 실행하면 이어서 진행한다.
5. **결과(2026-10-13)**
   - 25곳은 15곳씩 채웠다.
   - 실제로 행정구역 안에 같은 진료과가 적은 곳은 그대로 적게 붙였다. 르미엘(종로구 성형외과) 4곳, 성모하와유(부평구 외과) 3곳, 일산다나은(고양시 한방병원) 8곳이다.
   - 고유 경쟁병원은 346곳이다(병원별 연결 390건).
   - 강남제이스타의 기존 22곳은 실측 목록이라 다시 뽑지 않고 그대로 둔다.

## 2. 설정 구조

- `config/competitors_config.json`의 경쟁병원마다 `for_hospitals: [자사 hospital_id…]`를 둔다. 같은 경쟁병원은 한 번만 등록하고 한 번만 수집한다.
- 신규 `competitor_id`는 `comp_k<카카오 장소 ID>`다(안정적이고 고유함). 기존 22곳의 ID는 그대로 둔다.
- `hospitals_meta.json`의 병원별 `competitors` 배열(id/name/lat/lng)은 `build_meta.py`가 설정에서 자동으로 만든다. 일치 여부는 테스트로 검증한다.

## 3. 매일 수집 90분 맞추기 (`main.py`)

- 자사 병원은 매일 전부 수집한다(약 30분).
- **경쟁병원 순번**
  - `competitor_id` 순으로 정렬한 뒤, k번째 병원을 `k % G` 그룹에 넣는다(교차 배정). `G = ceil(N / 하루 정원)`이다.
  - 하루 정원은 `COMPETITOR_DAILY_CAPACITY = 80`이다. 90분 ÷ 실측 평균 66초로 잡았다.
  - 오늘 그룹은 `(KST 오늘 − 기준일 2026-10-14).days % G`로 정한다. 날짜만으로 정해지니 상태 저장이 필요 없고, 다시 실행해도 같은 그룹이 나온다.
- **시간 제한**
  - 경쟁병원 수집 누적 시간이 90분을 넘으면 남은 곳은 건너뛰고 `::warning`으로 건너뛴 수를 남긴다.
  - 워크플로에는 `timeout-minutes: 180`을 건다.
- **수동 실행**: `workflow_dispatch` 입력 `competitor_group`을 환경변수 `COMPETITOR_GROUP`으로 넘긴다.
  - 비어 있으면 오늘 그룹을 수집한다.
  - `all`이면 전체를 수집한다.
  - 숫자면 그 그룹을 수집한다.
  - `--hospital`로 특정 ID를 지정하면 순번과 무관하게 그 병원만 수집한다.
- **수집 간격이 생겨도 문제없는 이유**
  - 경쟁병원은 G일(예상 5일)에 한 번 수집된다. 네이버는 한 번에 최근 30건을 받으므로, G일 사이 신규가 30건을 넘지 않는 한 빠지는 리뷰가 없다.
  - VOC 급증 판정은 작성일 기준이라 수집 간격의 영향을 받지 않는다.
  - 화면에 "경쟁병원 리뷰는 약 G일 간격으로 갱신" 안내를 넣는다.

## 4. 검증

- 단위 테스트
  - 선정·필터·점수·동점 처리
  - 주소·이름 매칭(지번 "194 23번지" 형식 포함)
  - 그룹 배정: 모든 경쟁병원이 G일 안에 정확히 한 번 수집되는지, 날짜가 같으면 그룹도 같은지
  - 시간 제한에서 멈추는지
  - 자사 병원은 항상 수집되는지
  - meta와 config가 일치하는지
- 로컬 화면 확인: 병원 화면의 지도 마커·드롭다운·JS 오류
- 반영은 13시 수집이 끝난 뒤 push한다. push 후 수동 실행으로 한 그룹의 실제 소요 시간을 재고, 66초 가정과 차이가 크면 정원을 조정한다.
